# 메일로 받은 계정 삭제 요청 처리 절차 (#778)

계정 삭제 안내 페이지(`docs/legal/account-deletion.md`) 2절과 처리방침 4절·6절·9절은 "앱 없이 메일로 요청하면 삭제한다"고 안내한다. 이 문서는 그 요청을 운영자가 처리하는 방법이다.

- 대상: 앱을 설치하지 않았거나 로그인할 수 없는 사용자, 가입(닉네임 설정)을 마치지 않아 앱에서 탈퇴할 수 없는 계정
- 도구: `functions/scripts/deleteAccountByEmail.js` — 앱 탈퇴(`deleteAccount`)와 같은 함수(`functions/accountDeletion.js`의 `deleteUserData`·`deleteAuthUser`)로 **같은 범위**를 지운다 (지우는 것·익명화하는 것은 계정 삭제 안내 3절과 같다)
- 순서: 접수 → 본인 확인 가(메일 발신 인증, 안 되면 다의 확인 코드) → 대상 확인(dry-run, From 주소로) → 본인 확인 나(주소 검산) → (신고·제보 요청이 있으면 6절) → 실행 → 회신. From이 아닌 주소의 계정에 대한 요청은 dry-run 없이 3절 라

> ⚠️ Firebase 프로젝트는 `plant-82b09` 하나뿐이고 이것이 운영 환경이다. 스크립트는 실제 계정과 데이터를 지우며 되돌릴 수 없다 (복원은 `docs/FIRESTORE_BACKUP.md`의 백업뿐이고, 계정 하나만 되살리는 절차는 없다).

## 1. 준비 (처음 한 번)

1. 메인 폴더에서 함수 패키지를 설치한다 (스크립트가 `firebase-admin`을 쓴다)

```powershell
npm --prefix functions ci
```

2. 서비스 계정 키를 받는다: Firebase 콘솔 > Settings > Service accounts 탭 > "Generate New Private Key" → "Generate Key" ([Admin SDK 설정](https://firebase.google.com/docs/admin/setup) 문서 기준. 한국어 화면의 메뉴 이름은 확인하지 않았다)
   - 받은 JSON 파일은 **레포 밖**(예: 사용자 폴더의 별도 폴더)에 둔다. 레포 안에 두거나 커밋하지 않는다. 이 키로 Admin SDK가 운영 프로젝트의 Firebase 서버 API를 호출하며, 공식 문서도 서비스 계정 키는 매우 높은 보안 주의가 필요하다고 경고한다
   - 다 쓰고 나면 Google Cloud 콘솔에서 그 키를 삭제하고 파일도 지우는 것을 권장한다 (요청이 올 때마다 새로 받는다). 키를 삭제하는 메뉴 위치(IAM 및 관리자 > 서비스 계정 > 키 탭으로 보임)는 확인하지 않았다
   - 이 키로 운영에 접속해 스크립트를 실행해 본 적은 아직 없다 (에뮬레이터로만 확인)
3. 연습은 에뮬레이터로 먼저 한다 (아래 7절)

## 2. 접수

- 받는 곳: 처리방침 12절·계정 삭제 안내 4절의 문의 메일
- 제목은 "Plant 계정 삭제 요청"으로 안내했지만, 제목이 달라도 삭제를 요청하는 메일이면 처리한다
- 처리는 지체 없이 한다 (계정 삭제 안내 2절 3번)
- 신고·제보 내용 속 개인정보 삭제 요청이 함께 있으면 계정 삭제를 실행하기 **전에** 6절을 처리한다

## 3. 본인 확인

- 삭제 대상은 항상 **요청 메일 헤더의 보낸 사람(From) 주소**의 계정이다. 4절의 `--email`에는 From 주소를 그대로 넣고, 본문에 적힌 다른 주소는 쓰지 않는다
- 본문에서 From이 아닌 다른 주소의 계정을 지워 달라는 요청(계정 분실, 보호자 요청 포함)은 dry-run을 하지 않는다 → 라 또는 8절
- dry-run(계정 조회)은 가를 통과했거나 다의 확인 코드를 받은 뒤에만 한다. 그 전에는 계정이 있는지에 따라 달라지는 회신을 보내지 않는다. 계정 유무에 따라 회신이 달라지면 위조 메일이나 남의 주소를 묻는 메일을 보낸 사람이 Plant 가입 여부를 알 수 있기 때문이다

### 가. 메일 발신 인증 (dry-run 전)

| 확인 | 방법 | 이유 |
|------|------|------|
| 발신 인증 | Gmail 웹에서 메일을 열고 ⋮ > "원본 보기" → 위쪽 표에서 DMARC가 `PASS`인지 확인. 보낸 사람 주소의 도메인이 DMARC를 쓰지 않으면, DKIM이 `PASS`이고 서명 도메인(`Authentication-Results`의 `dkim=pass header.d=`)이 보낸 사람 주소의 도메인과 같을 때 통과로 본다. SPF는 참고만 한다 | 보낸 사람(From) 주소는 위조할 수 있다. SPF는 봉투 발신자(MAIL FROM)의 도메인을 인증하는데 이 도메인은 From과 다를 수 있고, 유효한 DKIM 서명이 있다는 것만으로는 From 도메인을 믿을 수 없다. DMARC는 SPF나 DKIM 중 하나가 From 도메인과 맞는(정렬된) 상태로 통과해야 `pass`다 (RFC 7489 기준, 지금은 RFC 9989~9991로 대체됨). DMARC가 없을 때의 DKIM 기준은 RFC의 기본값(같은 조직 도메인이면 정렬)보다 엄격하게, 같은 도메인만 인정한다 |
| `Reply-To` | "원본 보기"에 `Reply-To`가 있으면 보낸 사람 주소와 같은지 확인 | RFC 5322 3.6.2절은 `Reply-To`가 있으면 답장을 그 주소로 보내도록 제안한다. 그래서 위조 메일이 회신을 다른 사람에게 받아 가는 데 쓸 수 있다 |

- 둘 다 맞으면 4절 가(dry-run)로 간다
- 아래 경우는 모두 dry-run을 하지 않고 다의 확인 코드로 간다
  - 발신 인증이 통과하지 못함 (DMARC `FAIL`, 서명 도메인이 다른 DKIM만 있음 등)
  - 판정할 수 없음 (DMARC를 쓰지 않는 도메인인데 같은 도메인의 DKIM 서명도 없음)
  - `Reply-To`가 보낸 사람 주소와 다름
  - 같은 도메인 사용자의 위조가 의심됨: DMARC·DKIM은 메일이 그 **도메인**에서 왔다는 것만 확인한다. 같은 도메인의 다른 사용자가 From을 바꿔 보내는 것까지 막는지는 메일 서비스의 정책에 달렸고, 확인하지 않았다 (미확인). 회사·학교 도메인처럼 의심되면 다를 쓴다
- 확인 코드 메일은 From 주소로만 가므로, 위조된 요청이면 진짜 주소 주인에게 가고 위조한 사람은 받지 못한다. 계정이 있는지와 상관없이 같은 메일이라 가입 여부도 드러나지 않는다
- "원본 보기" 화면 이름·위치는 Gmail 화면 기준이며, 이 문서를 쓸 때 실제 요청 메일로 확인하지는 않았다 (미확인). 화면이 다르면 메일 헤더의 `Authentication-Results` 줄에서 `dmarc=pass`, 또는 `dkim=pass`와 그 뒤의 `header.d=`(서명 도메인)를 찾는다. DMARC를 쓰지 않는 도메인의 결과가 Gmail에 어떻게 표시되는지도 확인하지 않았다 (미확인)

### 나. 주소 검산 (dry-run 후)

| 확인 | 방법 | 이유 |
|------|------|------|
| dry-run 출력의 `이메일` = From 주소 | `--email`에 From 주소를 넣었으므로 보통 같다. 대소문자만 다르면 같은 주소로 본다. 그 밖에 다르면(점(.)·`+` 이후 등) 입력을 잘못 넣은 것이므로, 회신하지 않고 멈춘 뒤 `--email`을 다시 확인한다 | 계정 삭제 안내 2절: "해당 주소에서 보낸 메일만 처리". 스크립트의 계정 조회는 대소문자를 가리지 않았다 (에뮬레이터 기준, 4절 가) |

### 다. 확인 코드 (가에서 넘어온 경우)

1. 확인 코드를 만든다

```powershell
node -e "console.log(require('crypto').randomInt(100000, 1000000))"
```

2. 요청 메일의 보낸 사람(From) 주소로 **새 메일**(답장이 아님)을 보내 코드를 전달한다 (5절 "확인 코드" 문구). 답장으로 보내면 `Reply-To`로 갈 수 있다
3. 그 코드가 들어간 회신이 오면 가를 통과한 것으로 보고 4절 가(dry-run)로 넘어간다. 코드를 받은 메일함을 가진 사람이라는 것이 확인이므로, 이 회신의 발신 인증은 다시 보지 않는다
4. 코드가 들어간 회신이 오지 않으면 처리하지 않고, 다른 회신도 보내지 않는다. 코드는 처리가 끝나면 버리고 레포·이슈에 적지 않는다

### 라. 다른 주소의 계정에 대한 요청 (계정 분실 등)

- 로그인에 쓴 Google 계정을 잃어 그 주소로 메일을 보낼 수 없다는 요청처럼, From이 아닌 다른 주소의 계정을 지워 달라는 요청은 처리하지 않는다. dry-run도 하지 않고, 5절 "다른 주소의 계정" 회신(계정 유무와 상관없이 같은 문구)을 From 주소로 보낸다. 계정 삭제 안내 2절·처리방침 4절·6절이 이렇게 안내한다 (Google 계정 복구로 되찾은 뒤 그 주소에서 요청)
  - 다른 확인 방법(닉네임·화분 이름·가입 시기 등)을 두지 않은 이유: 닉네임은 커뮤니티에 공개되어 있어 남이 알 수 있고, 잘못 확인하면 남의 계정을 되돌릴 수 없게 지운다. Google 계정 복구는 Google이 본인 확인을 한다
  - 복구하지 못하면 메일로는 삭제할 수 없고, 계정과 데이터는 그대로 남는다
- 보호자(법정대리인)의 요청은 8절

메인 폴더의 `functions` 폴더에서 실행한다. 키 파일 경로는 실제 위치로 바꾼다.

```powershell
cd functions
```

```powershell
$env:GOOGLE_APPLICATION_CREDENTIALS = "C:\경로\키파일.json"
```

### 가. 대상 확인 (dry-run, 아무것도 지우지 않음)

```powershell
node scripts/deleteAccountByEmail.js --project plant-82b09 --email 보낸사람@gmail.com --dry-run
```

출력 예 (값은 계정마다 다르다):

```
접속 대상: 운영 서버 / 프로젝트: plant-82b09
삭제 대상 계정:
  uid          : ...
  이메일       : 보낸사람@gmail.com
  로그인 방식  : google.com
  계정 생성    : ...
  최근 로그인  : ...
  가입 상태    : 가입 완료
  닉네임       : ...
  화분 2개 · 게시글 1개 · 댓글 3개
dry-run: 아무것도 지우지 않았습니다.
```

- `접속 대상`이 `운영 서버`이고 프로젝트가 `plant-82b09`인지 본다 (에뮬레이터 환경 변수가 남아 있으면 `에뮬레이터`로 나온다)
- `이메일`이 From 주소와 같은지 3절 나대로 검산한다
- `가입 상태`는 셋 중 하나다. 어느 것이든 그대로 진행한다 (있는 데이터만 지우고 Auth 계정을 지운다)
  - `가입 완료`
  - `users 문서는 있으나 닉네임 설정 전 (가입을 마치지 않음)`
  - `users 문서 없음 (가입을 마치지 않음)` — Google 로그인 뒤 앱이 users 문서를 만들기 전에 끊겼거나(앱 종료·네트워크 오류), 지난 실행이나 앱 탈퇴가 users 문서까지 지운 뒤 Auth 계정을 지우기 전에 끊긴 경우 등
- `계정 없음: ...`이 나오면(종료 코드 2) 아무것도 지우지 않은 것이다 → 5절 "계정 없음" 회신 (6절의 신고·제보 요청만 받은 경우는 6절 표를 따른다. 3절 가를 통과했거나 3절 다의 확인 코드를 받은 요청에만 보낸다. dry-run은 그 뒤에만 하므로 이 순서를 지키면 된다). 이미 삭제된 계정에 다시 실행해도 이렇게 나온다. 단, 직전에 uid를 입력해 삭제를 진행한 실행(`--dry-run` 없음)이 `실패:`로 끝났다면 4절 나의 `실패:` 항목을 따른다. 직전 실패가 dry-run이었다면(키 설정 누락·네트워크 오류 등) 아무것도 지우지 않았으므로 그대로 "계정 없음" 회신이다
  - 주소에 점(.)·대소문자 차이가 있어도 같은 Gmail 계정일 수 있다. 계정 없음이 나오면 회신으로 Plant에 로그인할 때 고른 Google 계정 주소를 다시 확인해 달라고 한다 (에뮬레이터에서는 대문자가 섞인 주소로 만든 계정이 소문자로 저장되고, 대소문자를 바꿔 찾아도 같은 계정이 나왔다. 운영 Auth의 동작과 점(.) 차이는 미확인)

### 나. 실제 삭제

`--dry-run`을 빼고 같은 명령을 실행한다.

```powershell
node scripts/deleteAccountByEmail.js --project plant-82b09 --email 보낸사람@gmail.com
```

- 대상 계정을 다시 보여 준 뒤 uid 입력을 받는다. 화면의 uid를 **그대로** 입력해야 진행된다 (다른 값을 넣거나 입력 없이 끝내면 "취소"로 끝나고 아무것도 지우지 않는다, 종료 코드 3. 입력이 닫히는 경우는 유닛 테스트로 확인했고, 콘솔에서 Ctrl+C·Ctrl+Z로 끝내는 경우는 직접 확인하지 않았다)
- `삭제 완료: <uid> (Auth 계정·users 문서 없음 확인)`이 나오면 끝이다 (종료 코드 0)
- `실패: ...`(종료 코드 1)가 나오면 **같은 명령을 다시 실행**한다. 모든 단계가 다시 실행해도 안전하고, Auth 계정은 마지막에 지우므로 같은 이메일로 다시 찾아 남은 단계부터 이어서 처리된다
  - uid를 입력해 삭제를 진행한 실행이 `실패:`로 끝난 뒤 다시 실행했는데 `계정 없음`이 나오면, 그 실행이 데이터를 모두 지우고 Auth 계정까지 지운 뒤 그다음 단계(삭제 확인 등)에서 실패한 것이다. Auth 계정은 데이터 삭제가 끝난 뒤에만 지우기 때문이다 (8절대로 콘솔에서 Auth 계정을 먼저 지우지 않았다는 전제). 이때는 5절 "삭제 완료" 회신을 보낸다
  - 예외: 직전 실패 메시지가 `Auth 계정은 지워졌지만 users 문서가 남아 있음`이었다면 다시 실행해도 이메일로 찾을 수 없다. Firebase 콘솔 > Firestore에서 메시지에 나온 uid의 `users/{uid}` 문서와 하위 컬렉션을 지운 뒤 5절 "삭제 완료" 회신을 보낸다. 지우기 전에는 회신하지 않는다 (이 스크립트로는 처리하지 않는다. 콘솔에서 하위 컬렉션까지 지우는 메뉴 이름은 확인하지 않았다)
- 실행하면 앱 탈퇴 때와 같이 Firestore 트리거(화분 삭제 `onPotDeleted`, 댓글 수 `syncCommentCount*` 등)도 실행된다

### 다. 끝나면

```powershell
Remove-Item Env:GOOGLE_APPLICATION_CREDENTIALS
```

- 키 파일을 지우고, 1절 2번대로 콘솔에서 키를 삭제한다

## 5. 회신

회신은 항상 요청 메일의 보낸 사람(From) 주소로 보낸다. 답장 버튼을 쓰면 `Reply-To`가 있을 때 그 주소로 갈 수 있으므로(3절 가), 보내기 전에 받는 사람이 From 주소인지 확인한다. uid는 회신·이슈·레포에 적지 않고, 확인 코드는 확인 코드 메일에만 적는다.

**삭제 완료**

> 요청하신 Plant 계정과 데이터를 삭제했습니다. 삭제되는 데이터와 개인을 알아볼 수 없는 형태로 남는 데이터는 계정 삭제 안내(https://plant-82b09.web.app/account-deletion.html) 3절과 같습니다. 장애 복구용 백업에는 최대 7일 동안 남을 수 있으며 이후 자동으로 삭제됩니다.

**계정 없음**

> 이 주소로 가입한 Plant 계정을 찾지 못했습니다. 이미 삭제되었거나 다른 Google 계정으로 로그인하셨을 수 있습니다. Plant에 로그인할 때 고른 Google 계정의 주소에서 다시 보내 주세요.

**확인 코드** (3절 다. 답장이 아니라 보낸 사람 주소로 새 메일. 계정이 있는지와 상관없이 같은 문구)

> 이 주소에서 보낸 것으로 표시된 Plant 관련 요청(계정 삭제 또는 신고·제보 내용 삭제)을 받았습니다. 본인 확인을 위해 이 메일에 아래 확인 코드를 적어 회신해 주세요. 확인 코드: (코드). 요청하신 적이 없다면 이 메일은 무시하셔도 됩니다.

**다른 주소의 계정** (3절 라. 계정 분실 등 From이 아닌 주소의 계정에 대한 요청. 계정이 있는지와 상관없이 같은 문구)

> 본인 확인을 위해 Plant에 로그인할 때 사용한 Google 계정의 주소에서 보낸 요청만 처리합니다. Google 계정 복구(https://accounts.google.com/signin/recovery)로 계정을 되찾은 뒤 그 주소에서 다시 보내 주세요. 가입(닉네임 설정)을 마친 계정이라면 복구한 뒤 앱에서 직접 탈퇴하실 수도 있습니다.

**신고·제보 정보 요청** (6절. 찾을 단서가 없을 때)

> 신고·제보 내용 속 개인정보 삭제 요청을 받았습니다. 해당 신고·제보를 찾을 수 있도록 작성한 날짜(대략이라도)와 내용 일부를 알려 주세요.

**신고·제보 내용 삭제 완료** (6절)

> 요청하신 신고·제보 내용 속 개인정보를 지웠습니다. 신고·제보의 나머지 내용(대상·사유·처리 상태 등)은 신고 검토와 서비스 개선을 위해 남습니다.

## 6. 신고·제보 내용 속 개인정보 삭제 요청

신고 상세 내용(`reports`의 `detail`)이나 버그 제보·개선 제안 내용(`feedbacks`의 `description`, `reproductionSteps`)에 직접 적은 개인정보는 탈퇴해도 지워지지 않는다 (처리방침 3절 나 ※, 계정 삭제 안내 3절 나). 요청이 오면 Firebase 콘솔 > Firestore에서 해당 문서를 찾아 **개인정보 부분만** 지우도록 필드 값을 고친다. 문서 자체나 다른 필드(대상·사유·처리 상태·분류·앱 버전 등)는 신고 검토와 서비스 개선을 위해 그대로 둔다.

| 상황 | 찾는 방법 |
|------|----------|
| 먼저 | 계정 삭제 요청과 같이 3절 가(또는 다) → 4절 가의 dry-run(From 주소)을 한다. 6절만 요청한 경우도 같다 |
| dry-run에서 계정이 나옴 (아직 탈퇴 전) | 출력의 uid로 콘솔에서 `reports`·`feedbacks`를 `reporterId == <uid>`로 걸러 찾는다 |
| dry-run에서 `계정 없음` (이미 탈퇴함 등) | 탈퇴하면 `reporterId`가 `""`로 바뀌어 uid로 찾을 수 없다. 요청 메일에 적힌 작성 날짜·내용 일부로 찾는다: 콘솔에서 `createdAt`이 그 날짜 범위인 문서만 걸러, `reporterId`가 `""`인 문서의 내용을 하나씩 비교한다 (Firestore는 글자 일부로 검색하지 못한다). `reporterId == ""`와 날짜 범위를 함께 거는 조회는 복합 색인이 필요한데 `reports`·`feedbacks`에는 없으므로 날짜 범위만 건다. 신고는 탈퇴 때 새 ID로 옮겨지지만 `createdAt`은 그대로다 |
| 메일에 날짜·내용이 없음 | 찾을 수 없으므로 5절 "신고·제보 정보 요청" 회신을 보낸다 |
| 처리한 뒤 | 5절 "신고·제보 내용 삭제 완료" 회신. 계정 삭제도 요청했다면 계정 삭제까지 끝낸 뒤 "삭제 완료" 회신에 한 문장으로 함께 적어도 된다 |

- 탈퇴 뒤의 요청은 작성자 정보가 없어 본인인지 확인할 수 없다. 개인정보 부분을 지우는 것은 신고·제보의 쓰임을 해치지 않으므로, 메일의 날짜·내용이 문서와 맞으면 처리한다
- 계정 삭제와 함께 요청받았다면 **삭제를 실행하기 전에** 이 절을 먼저 처리한다 (삭제하면 `reporterId`가 비어 uid로 찾을 수 없다)

## 7. 에뮬레이터로 연습하기

운영에서 처음 실행하기 전에 에뮬레이터에서 같은 순서로 해 본다. 레포 루트에서:

```powershell
firebase emulators:start --only firestore,auth --project demo-plant
```

다른 터미널의 `functions` 폴더에서:

```powershell
$env:FIRESTORE_EMULATOR_HOST = "127.0.0.1:8080"; $env:FIREBASE_AUTH_EMULATOR_HOST = "127.0.0.1:9099"
```

- 에뮬레이터 UI(http://127.0.0.1:4000)의 Authentication에서 이메일이 있는 사용자를 하나 만들고, Firestore에 `users/<uid>` 문서 등을 넣은 뒤 4절 명령을 `--project demo-plant`로 실행한다
- 환경 변수를 둘 중 하나만 넣으면 스크립트가 실행하지 않는다 (Firestore와 Auth가 서로 다른 곳을 가리키게 되므로)
- 끝나면 `Remove-Item Env:FIRESTORE_EMULATOR_HOST, Env:FIREBASE_AUTH_EMULATOR_HOST`로 지운다. 남아 있으면 운영 실행이 에뮬레이터로 간다 (출력의 `접속 대상`으로 확인)

자동 테스트: `functions/test/integration/deleteAccountByEmail.test.js` (가입 완료·미완료·계정 없음·dry-run·입력 불일치·users 문서만 먼저 없어진 상태에서 재실행), `functions/test/unit/deleteAccountByEmailArgs.test.js` (인자·접속 대상·uid 입력). `npm --prefix functions test`로 실행한다.

## 8. 주의

- Firebase 콘솔의 Authentication에서 계정을 **먼저 지우지 않는다.** Auth 계정이 없으면 스크립트가 이메일로 uid를 찾을 수 없어 Firestore 데이터가 남는다 (이 스크립트는 uid로 직접 지우는 방법을 두지 않았다)
- 탈퇴 범위(`functions/accountDeletion.js`)를 바꾸면 앱 탈퇴와 이 스크립트에 함께 반영된다. 이때 계정 삭제 안내 3절·처리방침 3절도 함께 고친다 (`docs/LEGAL_HOSTING.md` 문서 수정 절차 4번)
- 스크립트(`functions/scripts`)는 함수 배포에 포함되지 않는다 (`firebase.json`의 `functions.ignore`)
- 처리방침 9절의 만 14세 미만 이용 확인에 따른 삭제와 보호자(법정대리인)의 요청은 이 절차의 대상이 아니며 따로 판단한다. 보호자 요청이 다른 주소에서 오면 dry-run을 하지 않고, 계정이 있는지 드러나지 않게 회신한다 (처리 방법은 따로 정한다)
